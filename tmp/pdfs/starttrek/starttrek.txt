Lunar Lander
Gymnasium

In this project, we will use Gymnasium, an API standard for reinforcement learning with a diverse collec-
tion of reference environments. The environment you'll use is Lunar Lander: a 2D rocket landing task built
on Box2D physics. It takes care of the inner workings of the lunar module, its representation, the physics
and the rendering, so that you can focus on the reinforcement learning part.




Parameters

      Actions


At each step, the agent picks one of 4 discrete actions:

       Action        Effect
         0           Do nothing
         1           Fire the left orientation engine
         2           Fire the main engine
         3           Fire the right orientation engine



      State


The state (or observation) returned by the environment is a vector of 8 values:



                                                     2
   Index      Name                     Description
     0        x                        Horizontal position (the landing pad is at 0)
     1        y                        Vertical position
     2        v_x                      Horizontal velocity
     3        v_y                      Vertical velocity
     4        theta                    Angle of the lander
     5        theta_dot                Angular velocity
     6        left_leg_contact         1 if the left leg touches the ground, 0 otherwise
     7        right_leg_contact        1 if the right leg touches the ground, 0 otherwise



        Reward


The reward is given at every step and is shaped to guide the lander toward a good landing:

 Event                                                          Reward
 Moving closer to / away from the landing pad                   Increases / decreases
 Moving slower / faster                                         Increases / decreases
 Lander tilted away from horizontal                             Decreases (the more tilted, the worse)
 Each leg in contact with the ground                            +10
 Each frame with a side engine ﬁring                            -0.03
 Each frame with the main engine ﬁring                          -0.3
 Safe landing (lander comes to rest)                            +100
 Crash                                                          -100



        End of an episode


 Type                   Cause
 terminated             The lander crashed (its body touched the ground)
 terminated             The lander left the viewport (x out of bounds)
 terminated             The lander is at rest (”not awake”)
 truncated              The episode reached the maximum number of steps




   terminated and truncated do not mean the same thing. A terminated episode really ended, there is
   no future reward to expect. A truncated episode was simply cut short, the lander could have kept
   going. Your algorithms must treat these two cases differently.

Usage

Here is a complete episode played by an agent that picks its actions at random:

  import gymnasium as gym

  # Create the environment ("human" opens a display window, use None to train faster)
  env = gym.make("LunarLander-v3", render_mode="human")

  # Start a new episode: we get the first state
  state, info = env.reset(seed=42)
  total_reward = 0.0
  done = False

  while not done:
      # Choose an action (here: at random, among the 4 possible actions)
      action = env.action_space.sample()

      # Apply the action: the environment returns what happened
      next_state, reward, terminated, truncated, info = env.step(action)

      total_reward += reward
      state = next_state
      done = terminated or truncated

  print(f"Episode finished with a score of {total_reward:.1f}")
  env.close()


Your agents will replace env.action_space.sample() with a decision based on state.

Reinforcement Learning
Every reinforcement learning algorithm relies on the same building blocks: an environment, a way to store
what the agent experienced, a way to choose actions, and a loop that makes the agent play and learn.

You will implement these building blocks in each of your two notebooks, adapted to the algorithm of that
notebook. The DQN and PPO sections that follow tell you what each algorithm needs on top of them.



Environment initialization

Your code must create and conﬁgure the environment in a controlled way:


  ✓ Training and evaluation do not need the same rendering mode. Rendering every frame is very slow.
  ✓ Your code must read the size of the state and the number of actions from the environment instead
    of hard-coding them.



Experience storage

An agent learns from what it lived. Each step it plays produces an experience (or transition):

 Element                   Meaning
 state                     The state the agent was in
 action                    The action it took
 reward                    The reward it received
 next_state                The state it ended up in
 done                      Whether the episode really ended after this step


These experiences must be stored until the agent learns from them. How long they are kept, how many
are kept, and in which order they are used depends on the algorithm:


  ✓ some algorithms keep a large memory of past experiences and learn from them many times
  ✓ others only learn from the experiences they just collected, then throw them away


Whatever the algorithm, your storage must return the experiences in a format ready to be used by a neural
network (tensors grouped by element, not a list of tuples).




   Think carefully about what you store in done, given the difference between terminated and truncated.

Episodes, steps and training

The training loop ties everything together. It runs many episodes, each made of many steps. At each
step, the agent observes the state, chooses an action, receives a reward, stores the experience and, when
relevant, learns from what it stored.

  ✓ log, for each episode: total reward, number of steps, and why it ended (crash, out of viewport, at

  ✓ regularly evaluate the agent on a few episodes without exploration, and keep track of the best ver-

  ✓ produce curves you will analyze in your report: reward per episode (and its moving average), episode

Deep Q Network
Q-values

A Q-value Q(s, a) is the total reward an agent can expect to collect if it takes action a in state s, then keeps
acting well afterwards. If the agent knew the true Q-values, choosing the best action would be easy: pick
the action with the highest Q-value.

Future rewards are worth a bit less than immediate ones: they are multiplied by a discount factor γ
(gamma), between 0 and 1. The Q-values follow the Bellman equation:


                                         Q(s, a) = r + γ max
                                                          ′
                                                             Q(s′ , a′ )
                                                             a


”The value of an action is the reward it brings now, plus the discounted value of the best action available
afterwards.”



Deep Q Network

The state of the lander is continuous: there are inﬁnitely many possible states, so we can't store a table
of Q-values. A Deep Q Network (DQN) uses a neural network to estimate them: it takes a state as input,
and outputs one Q-value per action.

The network learns by making its prediction Q(s, a) closer to a target built with the Bellman equation from
a stored experience:


                                       target = r + γ max
                                                       ′
                                                          Qtarget (s′ , a′ )
                                                         a


If the episode really ended after this step, there is no future: the target is simply r.

Computing the target with the network you are training is unstable: every update moves the target you
are aiming at. This is why DQN uses a second network, the target network: a copy of the main network,
updated less often, used only to compute the targets.

Replay buffer

Consecutive steps of an episode are strongly correlated: the state at step t + 1 is almost the same as
the state at step t. Learning from them in order makes training unstable. DQN stores its experiences in a
replay buffer, so that it can learn from a random mix of them, and reuse each experience several times.

Your replay buffer is the experience storage of your DQN agent. It must:

  ✓ have a fixed maximum capacity: once full, the oldest experiences are replaced by the new ones
  ✓ be able to return a random batch of experiences
  ✓ tell how many experiences it currently holds (learning should not start before there are enough of
    them)



Epsilon-greedy action selection

DQN always knows which action it believes is the best: the one with the highest Q-value. To keep exploring,
it uses the epsilon-greedy strategy, based on a single number ε between 0 and 1:

  ✓ with probability ε, the agent picks a random action (exploration)
  ✓ otherwise, it picks the action with the highest Q-value (exploitation)

ε starts high (the agent knows nothing yet) and decays over time down to a minimum value. You must
choose and justify how it decays (linearly, exponentially, per step, per episode...).

Proximal Policy Optimization
From values to policies

DQN is value-based: it learns how good each action is, and its behavior (or policy) is deduced from those
values. Policy-based methods take another approach: they learn the policy directly, as a probability
distribution over the actions for each state. The agent then samples its action from this distribution: ex-
ploration is built in, no epsilon-greedy needed.

Proximal Policy Optimization (PPO) is one of the most widely used policy-based algorithms.



Key elements

 Element                  Meaning
 Actor                    Network that outputs the policy: one probability per action for a given state
 Critic                   Network that estimates the value V (s) of a state
 Value V (s)              Total reward the agent can expect from state s by following its current policy
 Advantage A              How much better an action turned out to be compared to what the critic
                          expected. Positive: the action should become more likely. Negative: less
                          likely
 Rollout                  A batch of experiences collected by the current policy, used for a few
                          updates, then discarded
 Ratio                    Probability of an action under the new policy, divided by its probability under
                          the policy that collected it
 Clipping                 Limits the ratio to [1 − ϵclip , 1 + ϵclip ] so that one update can't change the
                          policy too much
 Entropy                  Measures how random the policy is. A bonus on entropy prevents the policy
                          from becoming certain too early




   The actor and the critic can be two separate networks, or a single network with two outputs
   (”heads”). Both approaches are valid: choose one and justify it.




How PPO learns

  1. The agent plays with its current policy and stores a rollout of experiences, along with the probability
     of each chosen action and the critic's value of each state.
  2. When the rollout is complete, the advantages are computed for every step. Look into Generalized
     Advantage Estimation (GAE), the standard way to compute them.
  3. The agent learns from the rollout over a few epochs, using mini-batches. Its loss combines three


                                                     9
     terms:
       ✓ the clipped policy loss, which pushes up the probability of actions with a positive advantage,
          without moving too far from the policy that collected the data
       ✓ the value loss, the MSE between the critic's predictions and the actual returns
       ✓ the entropy bonus, which keeps the agent exploring
  4. The rollout is discarded and the cycle starts again.




   PPO does not use a replay buffer: it can only learn from experiences collected by its current policy.
   Its experience storage is a rollout storage, emptied after every update, and it must hold more than
   the transitions of the previous section (action probabilities, values, advantages...).
